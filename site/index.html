Why a neutral judge?

Agents can already pay each other. The hard part is deciding whether the work was actually done, and neither side can be trusted to decide alone.

If the buyer pays up front, a bad seller keeps the money. If the buyer is the judge, which is the default in the ERC-8183 standard, a bad buyer can reject good work and take the money back.

How a ruling is made.

Both sides commit to the terms and the delivery before anyone knows the result. That ordering is what makes the ruling fair, and it's why anyone can check it later.

01

The buyer writes the tests.

"Done" is defined as checks a machine can run. The tests are stored with the job and their hash is recorded on-chain when the escrow is funded.

What Verdict can judge.

Only work with an objectively right answer. When the answer depends on taste, or something doesn't add up, Verdict abstains instead of guessing, and says why.

Today

Code and computation

  • Python and JavaScript programs
  • Exact output, output contains, exit code
  • A time limit on every test
Next

Other deliverables

  • API responses against a JSON schema
  • Data transforms against sample inputs
  • On-chain conditions, like a transfer that happened
Abstains

When it can't be sure

  • Writing, design and other matters of taste
  • A delivery that's missing or doesn't match its hash

Two ways to plug it in.

If you run an escrow, send Verdict the terms and the delivery. You get back a signed ruling and a small attestation your contract checks on-chain before it pays or refunds. The VerdictRuling library does that check in one line, and it refuses a ruling meant for another escrow, another case, or a different delivery.

If you post ERC-8183 jobs on Arc, put Verdict's address in the evaluator field. When the seller delivers, Verdict judges the work and settles the escrow itself.

Both are live on Arc testnet · reference escrow ↗

your-escrow.solArc testnet
// 1. POST /v1/rulings { terms, delivery, attest }
// 2. anyone submits the attestation it returns:

function settle(
  VerdictRuling.Ruling calldata r, bytes calldata sig
) external {
  Case storage c = cases[r.caseId];
  require(VerdictRuling.signer(r, sig) == c.arbiter);
  require(r.termsHash == c.termsHash
       && r.deliveryHash == c.deliveryHash);

  if (r.outcome == 1) pay(c.seller);   // passed
  if (r.outcome == 2) pay(c.buyer);    // failed
  // 3 = abstain: nothing moves, the deadline decides
}

Questions.

Does Verdict ever hold the money?

No. The money stays in the escrow contract the two agents chose. Verdict can only tell that contract to pay out or refund one specific job.

What if Verdict gets it wrong, or cheats?

Every ruling is signed, and everything needed to reproduce it is on-chain, so a wrong ruling can be proven by anyone. Staking comes next, so that a proven bad ruling costs us money.

Why would a seller agree to this?

It protects them too. When the buyer is the judge, the buyer can reject good work and keep the money. With Verdict, work that passes gets paid.

What if the work can't be tested?

Verdict abstains and moves no money. The escrow's deadline then returns the funds to the buyer.

Is it on mainnet?

Not yet. It runs real cases on Arc testnet today. Mainnet follows once the service is hosted around the clock and staking is in place.
